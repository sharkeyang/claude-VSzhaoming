# 问题总结：谕组周 CSV 的 `中符串周` 列编码错误，导致等类判断失效

> 生成日期：2026-10-08
> 用途：交接给其他 AI 继续调查

## 一、现象

**P1 赛马脚本匹配率极低（13.8%）**。VBA 端查表时，`周策分P1` 大量为 `_`（匹配不到）。

## 二、根因链

**1. `中符串周` 列的值是数字 `0-5`，不是字母 `A-F`**

- 元数据表（`_产出物/_工具/元数据_vba数据映射_周类.md`）确认：`中符串周`（44列）= `位谕of周管中符串`。
- VBA 内部 `中符串` 是**字母 `A-F`**（结算.bas 760-772行，`值单形中符 = 常枚中符上全("A")` 等）。
- 但 CSV 导出的 `中符串周` 是**数字**（如 `0`/`4010`/`3010`/`3100`），末位是 `0-5`。

**2. 等类判断依赖字母末位，但末位是数字 → 等2/等3/等6/等7 全部失效**

- VBA 端 `周等类`（神谕.bas 1526-1548行）：`InStr("AB", 周末符)` 判断末位字母。
- P1 脚本（`vba表周策分P1.py` 66-70行）：`wk['末位'].isin(['C','D','E','F'])` 判断末位字母。
- 但 `中符串周` 末位是数字 `0-5`，字母判断永远失败 → 等2/等3/等6/等7 为空。
- **P1.txt 只有等1 和等5**（ZA=1 和 ZA=-1 不依赖末位），等2/等3/等6/等7 缺失。

**3. 匹配率低的原因**

- P1.txt 只有 46 个 key（等1/等5），而 VBA 端构造的 key 覆盖了等6/等3 等，这些匹配不到 P1.txt。

## 三、关键矛盾点（需要继续调查）

**VBA 内部 `中符串` 是字母，CSV 导出是数字，但导出代码（1771行）直接导出 `谕组(X, 位谕of周管中符串)`，无转换。**

- `位谕of周管中符串` 在 1223行被赋值为 `组结算(X, 基位周类 + 位os具中符串)`。
- `组结算(X, 基位周类 + 位os具中符串)` = `ARROSW(位os具中符串)`（结算管理.bas 794行）。
- `ARROSW(位os具中符串)` 在结算.bas 774行被赋值为 `Right(...) & 值单形中符`（字母）。

**所以理论上 `中符串周` 应该是字母，但实际是数字。** 需要定位数字编码的来源——可能在 `组结算` 数组填充、`ARROSW` 填充、或导出链路中某处被转换。

## 四、已确认的事实

1. **VBA 内部 `中符串` 是字母 `A-F`**（结算.bas 760-772行，`值单形中符 = 常枚中符上全("A")` 等）。
2. **CSV 导出 `中符串周` 是数字 `0-5`**（如 `0`/`4010`/`3010`/`3100`）。
3. **元数据表确认** `中符串周`（44列）= `位谕of周管中符串`。
4. **等类判断用字母**（VBA端 `InStr("AB", 末位)`，P1脚本 `['A','B']`），但末位是数字 → 等2/等3/等6/等7 失效。
5. **P1.txt 只有等1 和等5**，匹配率 13.8%。
6. **假设 `0=A、1=B、2=C、3=D、4=E、5=F` 后，等类为空降到 0**，等类分布合理（等6/等3/等5/等1/等2/等7）——但这个假设未最终确认。

## 五、可能的修复方向（需继续调查确认）

**方向A（根治）**：修复导出程序，让 `中符串周` 导出为字母 `A-F`，重新导出数据。这样等类判断（字母）自然恢复。

**方向B（快速）**：修复 P1 脚本和 VBA 端的等类判断，用数字 `0-5` 对应 `A-F`。但需先确认数字编码的真实含义。

**关键待确认**：`中符串周` 数字 `0-5` 是否对应 `A-F`？数字编码的来源在哪？
